## 1. Verdict

The backend is **genuinely engineered**, not a mock: Spree 6.0.4 exact-pinned,
Empire extensions as host-app migrations/models/services/controllers, real
request specs for authorization, and an E2E journey that drives the live API
end-to-end (seller application → approval → product publish → COD checkout →
capture → seller balance → payout review → sweep → B2B catalog/MOQ/PO → RFQ →
quote → accept). That is real.

The **storefront is a thin functional shell**, not the marketplace the mandate
describes: 14 routes, ~1,600 lines total, one hero plus four products on the
home page, no categories, no seller pages, no SEO layer at all, no design
system, no Dari webfont.

Two claims in the existing documentation are **factually wrong today**
(F-01, F-02) and one file is stale in a way that would silently break a fresh
install (F-03).

### F-02 — `render.yaml` says migrations run on boot; they do not — **HIGH**

- `render.yaml` header: *"Migrations run from the image entrypoint on boot."*
- `server/bin/docker-entrypoint` is, in full:
  ```bash
  #!/bin/bash -e
  # Migrations are a one-shot Compose service, never a race between web replicas.
  exec "$@"
  ```
  It runs no migration. `render.yaml` defines **no `preDeployCommand`** and no
  separate migrate service.
- Impact: a Render deploy boots Puma against an unmigrated database → every
  Empire table missing → `/api/v3/store/empire/*` 500s and no COD/geography.
  The Compose stacks are fine (they have a real `migrate` one-shot service);
  only the Render blueprint is wrong.
- Fix: add `preDeployCommand: bin/rails db:migrate db:seed` to the web service,
  or correct the comment and document a one-shot migrate service. **Not
  applied** — deployment configuration, needs your approval (your rule 6).

### F-03 — `db/schema.rb` does not contain the Empire tables — **HIGH**

- `server/db/schema.rb`: `ActiveRecord::Schema[8.1].define(version: 2026_11_02_132858)`.
- `server/db/migrate/` contains `20261113000001_create_empire_provinces`,
  `20261113000002_create_empire_districts`, `20261113000101_create_empire_rfqs`,
  `20261113000102_create_empire_quotes`, `20261113000103_create_empire_payout_requests`.
- `grep -n empire server/db/schema.rb` → **no match**.
- Impact: any `db:schema:load`, `db:setup` or `db:prepare` path builds a
  database **without** the five Empire tables. CI never hits this because
  `backend-ci.yml` runs `db:create db:migrate` (migration path), which is
  exactly why the drift is invisible.
- Fix: regenerate and commit `schema.rb` from a Ruby-enabled environment
  (`docker compose … migrate` writes it back through the bind mount, or add a
  CI step that fails when `git diff --exit-code server/db/schema.rb` is dirty).
  **Cannot be done in this sandbox (no Ruby).** Best available mitigation
  applied here: a CI guard so the drift can never recur silently.

### F-04 — Sellers cannot discover RFQs: the RFQ loop has no seller entry point — **HIGH**

- Routes (`server/config/routes.rb`):
  - `store/empire/rfqs` → index/show/create scoped to **the customer**
    (`visible` = own RFQs or own company's).
  - `seller/empire/quotes` → index/create only. **No RFQ listing.**
  - `admin/empire/rfqs` → index only (staff).
- `Api::V3::Seller::Empire::QuotesController#create` needs `params[:rfq_id]`.
  Nothing in the product tells a seller which RFQ ids exist.
- `storefront/e2e/marketplace-journey.spec.ts` obtains `rfq.id` from the buyer's
  own `POST` response and passes it straight to the seller call — it proves the
  API works, not that a seller can find work.
- UI check: `apps/seller-dashboard/src/plugins.ts` is literally `export {}`;
  the storefront has no `/seller/rfqs` page. **No seller anywhere can see an
  RFQ.**
- Impact: RFQ is an API-only feature. A real seller cannot use it. This is the
  difference between "implemented" and "usable".
- Fix: add `GET /api/v3/seller/empire/rfqs` (open/quoted RFQs in
  `current_seller.store` where `seller_id` is nil or the current seller, with
  the seller's existing quote embedded), a storefront `/seller/rfqs` page, and
  request specs. Also add `GET /api/v3/admin/empire/rfqs/:id` for staff review.

- Impact: the marketplace is effectively invisible to search engines, which for
  an Afghan B2B/B2C marketplace is a primary acquisition channel.

### F-09 — Customer JWT + refresh token live in `sessionStorage` — **MEDIUM**

- `storefront/src/lib/api.ts`:
  `SESSION_KEY = "empire.session.v1"` → `sessionStorage.setItem(..., {token, refresh_token})`.
  Cart reference in `localStorage` (`empire.cart.v1`).
- Contrast with `storefront/src/lib/staff-api.ts`, which is done correctly:
  admin/seller tokens are module-memory only and refresh reads an **HttpOnly
  cookie** set by the Spree auth controller (`credentials: "same-origin"`).
- Impact: one XSS on the storefront exfiltrates a long-lived customer refresh
  token. Combined with F-10 (no CSP) there is no second line of defence.
- Fix direction: adopt the staff pattern for customers (HttpOnly refresh
  cookie), or at minimum add a CSP. Not silently changed here — it touches the
  auth flow that E2E currently proves.

### F-13 — No Afghan phone validation — **LOW** (already documented, still open)

`docs/AFGHANISTAN-LOCALIZATION.md` admits it. Confirmed in code: the only

### F-14 — Tiered (volume) prices cannot be rendered on the PDP — **INFO**

The Store API `Price` schema exposes `amount`, `compare_at_amount`,
`price_list_id` — **no tier table**. `Variant` exposes
`minimum_order_quantity`, `order_multiple`, `units_per_carton`,
`purchase_unit`. Tiers exist server-side (`spree_price_adjustment_tiers`,
`20260915121229`) and are applied to the cart (the E2E asserts 10 units →
800 AFN), but a buyer cannot *see* the ladder before adding to cart.
MOQ and order-multiple **are** shown on the PDP today. Showing the ladder
requires a small Empire read endpoint — not implemented, and it must not be
faked in the UI.

### F-15 — Minor code-quality items — **LOW**

- `app/register/page.tsx`: `autoComplete={type === "password" ? "new-password" : name}`
  → the confirm-password field receives `autocomplete="password_confirmation"`,
  which is not a valid autofill token; browsers ignore it.
- `components/product-card.tsx` uses `next/image` with `unoptimized` →
  no resizing/AVIF/WebP; every thumbnail is served at original size. Combined
  with F-06 (no gallery) this is the main Core Web Vitals risk.
- `lib/api.ts` sends `X-Spree-Locale` by string-splitting `document.cookie`
  manually; fine, but it hardcodes `fa-AF` as the fallback rather than reading
  the locale from the provider.

### The two E2E failures nobody could see

Worth recording because it cost several CI cycles and the cause is not in this
repository's code. `product details open from the Backend catalog` failed with a
strict-mode violation: `getByTestId('product-link')` matched the demo product
twice. The cart test failed the same way on `add-to-cart`, and later the login
form matched `ایمیل` twice.

Runner logs cannot be downloaded in this environment, so the diagnosis went out
through workflow annotations: a probe of the Store API, then of the rendered HTML,
then of the live DOM sampled every 150ms.

The API was never at fault — `meta.count`, rows returned and distinct ids all
agreed, and the server-rendered HTML held exactly two cards with distinct hrefs.
In the browser, immediately after the `load` event, the document held **four**
product links and settled on two within 150ms, with no console output at all:

```
t+0ms    n=4   body children include DIV#S:0{hidden}
t+150ms  n=2   (and every later sample stays at 2)
console messages: 0
```

Server Components that fetch stream their HTML, and React parks each finished
segment in a hidden container before discarding it. For that window the document
holds the real cards plus inert copies. `getByTestId` and `getByLabel` count
hidden elements; `getByRole` does not, which is why every heading assertion on
those same pages always passed. A shopper never sees the copies — they are
`display: none`, unfocusable and absent from the accessibility tree.

`e2e/navigation.ts` now waits, after every navigation and reload, until no hidden
container holds rendered markup. That is safe to require permanently because
nothing in `src` sets the `hidden` attribute: decorative elements use
`aria-hidden`, responsive hiding uses Tailwind classes.

A separate real defect was found on the way and fixed in `d374876`: `ProductCard`
used the same `add-to-cart` test id as the buy box, so a product page with a
related-products rail offered several identically named "add to cart" buttons —
ambiguous for a screen-reader user, not only for a test.
